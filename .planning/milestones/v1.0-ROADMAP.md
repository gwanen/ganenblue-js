## Phase Details

### Phase 1: Skill Refresh Implementation

**Goal:** Bot reloads page after each skill usage in Full Auto mode, with GUI toggle (default: OFF) and persistent state.

**Requirements:** SKILL-01, SKILL-02, SKILL-03, SKILL-04, SKILL-05

**Success Criteria:**

1. After each skill is used in FA, the page reloads to skip the skill animation
2. GUI checkbox toggles skill refresh (default: unchecked/OFF)
3. State persists in localStorage across sessions
4. Does not trigger in Semi Auto mode

**Race condition handling:**

- When `battle:ability_used` fires, set `abilityUsed = true` flag
- In the `waitForBattleEnd` loop, check `abilityUsed` AFTER Priority 0 (boss died / party wiped / network finished)
- Only refresh if no higher-priority event is pending
- This prevents refreshing over a battle-end result

**Files to modify:**

- `src/bot/battle-handler.js`:
  - Add `this.skillRefresh` constructor option (default: false)
  - Add `onAbilityUsed` handler that sets `abilityUsed = true` (separate from `onAbilityOrSummon` timing handler)
  - Register `battle:ability_used` → `onAbilityUsed` in waitForBattleEnd listeners
  - Add reload block: after Priority 0 checks, before attack refresh, gated on `mode !== 'semi_auto' && abilityUsed && this.skillRefresh`
  - Unregister listener in cleanup
- `src/gui/index.html`:
  - Add "Refresh on Skill" checkbox (default: unchecked) in Options section for both p1 and p2
- `src/gui/renderer.js`:
  - Add `skillRefresh` to saveProfileSettings, loadProfileSettings, inputs array, and startBot settings

**Tests to add/verify:**

- `tests/battle-handler-logic.test.js` — verify abilityUsed flag + refresh behavior

### Phase 2: Network Listener Optimizations

**Goal:** Reduce CPU and memory overhead in the `_handleResponse` pipeline by filtering earlier, parsing later, and short-circuiting on resource types.

**Requirements:** NET-01, NET-02, NET-03, NET-04, NET-05

**Success Criteria:**

1. resourceType checked before URL pattern matching (avoids string ops on non-fetch/xhr/script)
2. `_hasBattleListeners()` guard extended to cover `battle:result` and `raid:*` events
3. Content-length pre-check skips JSON parse for oversized responses (>100KB)
4. Scenario `cmd` parsing uses lazy short-circuit instead of full `Array.find()` on every response
5. All existing tests pass; no regressions in battle behavior

**Optimizations (from analysis):**

| #   | Optimization                                          | Impact                         | Lines         |
| --- | ----------------------------------------------------- | ------------------------------ | ------------- |
| 1   | Swap resourceType before URL check                    | ~33% fewer string checks       | 2 lines       |
| 2   | Add battle:result + raid:\* to \_hasBattleListeners() | Skip parsing when no listeners | 4 lines       |
| 3   | Content-length check before JSON parse                | Skip 500KB+ responses          | 5 lines       |
| 4   | Lazy scenario parsing (only check terminal cmd)       | Biggest CPU win                | 10 lines      |
| 5   | Reorder URL filters for early bailout                 | Micro-optimization             | reorder block |

**Files to modify:**

- `src/core/network-listener.js` — all optimizations in `_handleResponse` and `_hasBattleListeners`

### Phase 3: Performance & Snappiness Optimizations

**Goal:** Achieve maximum interaction speed by replacing `clickSafe` with `cachedClick(0)` and reducing polling delays.

**Success Criteria:**
1. Polling interval for UI checks reduced from 100ms/200ms to 50ms.
2. Stability delay for all critical battle/summon clicks reduced to 0ms.
3. Redundant navigations in `runSingleQuest` consolidated into a single "hop".

### Phase 4: Logging Standardization & Formatting

**Goal:** Standardize all `this.logger` output to a unified "Rigid Formal" style for improved readability and professional console output.

**Success Criteria:**
1. Unified prefixes: `[Core]`, `[Quest]`, `[Battle]`, `[Status]`, `[Auth]`, `[Error]`.
2. Removal of all conversational ellipses (`...`) from log bodies.
3. Standardized error catch format: `[Error] Category: Action failure (Fault: message)`.
